# ranim one-shot 视频制作

核心方法：**一个 prompt，一次交付**。先做知识整理与叙事设计，再写场景
代码；屏幕上出现的每一个数字都必须来自真实实现（模拟器/算法 + 单元
测试），没有任何手写的动画数值；每轮全片渲染后抽帧目检，逐条记录
"问题 → 修复"，直到验收，最后按固定章节归档。

本 skill 刻意不规定"怎么做"。叙事结构、场景组织、代码架构与视觉风格
都是自由的，唯一的边界是 §2 的真实性不变量；它传递的只有验收标准
（§1/§2/§4–6）和已知坑（§3）。

前置：一个可用的 ranim 开发环境（匹配的工具链、ranim-cli、ffmpeg）。
从哪里开始工作、交付到哪里，遵循所在项目的约定（通常在其 AGENTS.md）。

## 1. 设计先行

写代码之前，把三件事想清楚并落成文字（归档 README 设计章节的素材）：

- **受众**：默认"具备基础计算机素养但对本主题零了解"；每个术语首次
  出现必须自解释，类比先行，精确性随后。
- **弧线与分镜**：叙事弧线由内容决定，不要套模板——问题驱动、对比
  驱动、沿执行路径、由小放大，或任何别的组织方式都成立。落成 beat
  列表（每个 beat = 一句画面描述 + 时长估计），全片时长由内容决定，
  不为凑时长注水。
- **真实性规划**：明确哪些画面由真实实现驱动（计数、翻译、级联、状态
  机……），并为它们规划单元测试断言。如果一段动画的数字只能手写，
  重新设计这段动画。

## 2. 真实数据驱动（不变量）

- **输入精心构造并逐对验证**：演示数据要保证每个展示步骤的行为都符合
  预期、可独立复算。
- **真实实现内置在源码里**：把模拟器/算法写进 example，动画时间线由其
  输出的事件序列驱动——动画只是数据的视图。
- **单测锁行为**：`cargo test` 断言实现的关键行为（失败分支、变换结果、
  级联序列、回归不变量、复用行为……）。测试即动画正确性的锚。

## 3. 已知坑（ranim / typst）

与所选结构无关，遇到对应场景时直接规避：

- **typst markup**：`_` 触发强调，字面下划线要写 `\_`；`#`、`~` 会被吞
  掉，必须转义；em dash 前后留白偏宽，密集文案可用 `·`。
- **文字高亮**：对"文字放进容器"的物件，高亮只改容器的填充/描边；
  加宽字形描边会糊成色团。
- **按 key 查找物件**：警惕同 key 多实例与已消费实体——查找命中旧对象
  会让该消失的东西残留。用"标记消费 + 过滤查找"，不要边遍历边删除。
- **消费模拟输出**：对每个分支显式 `match`，不 `unwrap`——新引入的
  失败分支上的 unwrap 是渲染期 panic 的常见来源。

## 4. 渲染 → 目检 → 迭代

每轮循环：

1. **全片渲染**：`ranim render <topic> --example <topic> [--features ...]`，
   记录耗时与帧数。
2. **抽帧**：`reference/sample-frames.sh <mp4> <outdir> [N]`，每轮均匀抽
   15–30 个时点；capture 时点必抽，用视觉能力逐张读图。
3. **检查清单**：物件重叠 / 越出画幅或被裁切 / 该消失的残留物 / 时序
   错位 / 文字发糊 / 对比度不足。
4. **逐条记录"问题 → 修复"**：这是归档 README 迭代章节的素材，也是
   方法论本身的输入。诚实记录，包括渲染 panic。
5. 循环直到一轮抽检零新问题，再做终版：`ranim output` 出片 + 全片抽检
   复核（含全部 capture 时点）。

## 5. 验证

- `cargo check` / `clippy`（含 features）/ `fmt` / `test` 全绿零警告。
- 终版抽检：确认历史修复全部生效且无回归。
- `ranim output` 成片成功，mp4 与 captures 就位。

## 6. 归档

- 归档 README 使用固定章节（模板见
  `reference/run-readme-template.md`）：效果图 / 原始 prompt 逐字引用 /
  设计与实现思路 / 逐轮迭代记录（问题 → 修复）/ 验证情况 / 环境。
- 结构化元数据按项目约定的格式**如实**填写：自报信息标注来源，不确定
  就写 unknown，不编造。
- 迭代记录的价值在诚实：它们既是本次交付的审计线索，也是下一次方法论
  迭代的输入。
