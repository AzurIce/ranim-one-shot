# ranim one-shot 视频制作

核心方法：**一个 prompt，一次交付**。先做知识整理与叙事设计，再写场景
代码；屏幕上出现的每一个数字都必须来自真实实现（模拟器/算法 + 单元
测试），没有任何手写的动画数值；每轮全片渲染后抽帧目检，逐条记录
"问题 → 修复"，直到验收，最后按固定章节归档。

前置：一个可用的 ranim 开发环境（匹配的工具链、ranim-cli、ffmpeg）。
从哪里开始工作、交付到哪里，遵循所在项目的约定（通常在其 AGENTS.md），
本 skill 不规定。

## 1. 知识整理与叙事设计

写代码之前，先把讲什么、按什么顺序讲想清楚，落成文字（归档 README 设计
章节的素材，不是草稿）：

1. **受众模型**：默认"具备基础计算机素养但对本主题零了解"。每个术语
   第一次出现必须自解释；类比先行，精确性随后。
2. **叙事弧线**：先定一条弧线再填内容。常用骨架：钩子（抛出问题）→
   建立心智模型 → 遇到问题/对比方案 → 核心机制（可分多幕）→ 完整回放/
   点题收尾。实例："钩子→两难→算法→验证→意义"（BPE 讲解）、
   "钩子→虚构的地址空间→段的失败→页的胜利→伙伴批发→slab 零售→完整
   供应链"（内存分配讲解）。
3. **分幕与 beat 列表**：每一幕列出 beat（每个 beat = 一句话的画面描述
   + 时长估计），全片时长由内容决定，不为凑时长注水。
4. **真实性规划**：明确哪些画面由"真实实现"驱动（计数、翻译、级联、
   状态机……），并为它们规划单元测试断言。如果一段动画的数字只能手写，
   重新设计这段动画。

## 2. 真实数据驱动（本方法论的核心原则）

- **输入精心构造并验证**：演示用的语料/数据要逐对验证过每一步行为
  （例如一个迷你语料要保证每轮 merge 的最高频对都是唯一最大值且语义
  正确）。
- **内置真实实现**：把模拟器/算法写在 example 源码里（BPE 训练/编码、
  伙伴系统模拟、slab 状态机、首适应分配器……），动画时间线由其输出的
  **事件序列**驱动，动画只是数据的视图。
- **单测锁行为**：`cargo test` 断言实现的关键行为（失败分支、翻译结果、
  级联事件序列、回归不变量、复用行为……）。测试即动画正确性的锚。

## 3. 场景工程模式（ranim）

- **结构**：单 `#[scene]`，一个共享 `AnimStack`；每个物件组持有一条完整
  生命周期的 `AnimSequence`（`life_seq` 模式：fade in → morph 事件 →
  fade out → `hold_to(TOTAL)`），用 `forward_to`/`hold_to` 对齐共享时钟；
  幕与幕之间整幕淡出。参考 `reference/scene-skeleton.rs`（摘自既有交付
  实例；以当次 pin 的 API 为准编译验证）。
- **文字**：typst feature 的 `TextItem`（逐字形 VItem）。坑：markup 里
  `_` 触发强调（`task_struct` 必须写 `task\_struct`）、`#`/`~` 会被吞
  （必须转义）；em dash 前后留白偏宽，卡片文案可用 `·`。
- **高亮只刷盒子不刷字形**：chip 组的第 0 个 item 是方框；给字形加描边
  会糊成色团（实测踩过两次）。金色高亮一律只改 `items[0]`。
- **查找类 bug 防御**：按 key 查找物件时警惕同 key 多实例与"已死实体"
  （实例：Merge 推入同 key 新块后 `position()` 命中已消费的旧块，导致
  幽灵标签）。用"标记 consumed + 过滤查找"，不要从 vec 移除。
- **防御式消费模拟输出**：对模拟结果的每个分支显式 `match`，不 `unwrap`
  ——新引入的失败分支上的 `unwrap()` 是渲染期 panic 的常见来源。
- **capture**：`r.insert_time_mark(t, TimeMark::Capture("xx.png"))` 埋点，
  `preview.png` 是门面帧（选信息密度最高的一幕），另附 2–5 张关键时点
  capture，交付时复制进归档目录。
- **输出**：`#[output(dir = ...)]`，1920x1080 @60fps。索引不足时可手搓
  图形（如三线开放式箭头）而不是等上游支持。

## 4. 渲染 → 目检 → 迭代

每轮循环：

1. **全片渲染**：`ranim render <topic> --example <topic> [--features ...]`。
   记录耗时与帧数。
2. **抽帧**：`reference/sample-frames.sh <mp4> <outdir> [N]`，每轮均匀
   抽 15–30 个时点；capture 时点必抽，用视觉能力逐张读图。
3. **检查清单**：物件重叠 / 越出画幅或被裁切 / 该消失的残留物 / 时序
   错位（动画晚于/早于叙事）/ 文字发糊 / 配色对比度。
4. **逐条记录"问题 → 修复"**：这是归档 README 迭代章节的素材，也是
   改进本 skill 的素材。诚实记录，包括渲染 panic。
5. 循环直到一轮抽检零新问题，再做终版：`ranim output` 出片 + 全片
   抽检复核（含全部 capture 时点）。

## 5. 验证

- `cargo check` / `clippy`（含 features）/ `fmt` / `test` 全绿零警告。
- 终版抽检：确认历史修复全部生效且无回归。
- `ranim output` 成片成功，mp4 与 captures 就位。

## 6. 归档

- 归档 README 使用固定章节（模板见
  `reference/run-readme-template.md`）：效果图 / 原始 prompt 逐字引用 /
  设计与实现思路 / 逐轮迭代记录（问题 → 修复）/ 验证情况 / 环境。
- 结构化元数据（模型、harness、轮数、时长等）按项目约定的格式**如实**
  填写：自报信息标注来源，不确定就写 unknown，不编造。
- 迭代记录的价值在诚实：它们既是本次交付的审计线索，也是下一次
  方法论迭代的输入。
